# Integration Architecture — YouTube Organizer

_Generated: 2026-07-20 · Monorepo: frontend ⇄ backend ⇄ Google_

## Parts

| Part | Runtime | Local URL |
| --- | --- | --- |
| `frontend` | Next.js 15 (React 19) | `https://localhost:3000` |
| `backend` | Django 5.2 + DRF | `https://localhost:8000` |
| `db` | PostgreSQL 15 | `db:5432` (internal) |
| Google | OAuth2 + YouTube Data API v3 | external |

## Integration Points

### 1. Frontend → Backend (REST over credentialed HTTPS)

The **only** app-internal integration. All calls are browser `fetch` with
`credentials: "include"` so the `access_token` HttpOnly cookie rides along.

| From | To | Type | Endpoint | Purpose |
| --- | --- | --- | --- | --- |
| `YoutubeHeader` | backend | REST GET | `/api/auth/google/` | Get OAuth URL, then redirect to Google |
| `YoutubeHeader` | backend | REST GET | `/api/auth/me/` | Determine logged-in state |
| `usePlaylists` | backend | REST GET | `/api/youtube/playlists/` | Fetch the user's playlists |
| Browser (OAuth redirect) | backend | HTTP GET | `/api/oauth2callback/` | Google → backend callback |
| Backend (302) | `auth/callback` route | redirect | `/auth/callback` | Land back in the SPA after login |

**Contract source of truth:** [api-contracts-backend.md](./api-contracts-backend.md).

**Config knobs:**
- Frontend: `NEXT_PUBLIC_BACKEND_URL` (used by `YoutubeHeader`; `usePlaylists` currently
  hardcodes `https://localhost:8000`).
- Backend: `FRONTEND_AUTH_CALLBACK_URL`, `CORS_ALLOWED_ORIGINS = ["https://localhost:3000"]`.

### 2. Backend → Google (OAuth2 + YouTube Data API)

| From | To | Type | Purpose |
| --- | --- | --- | --- |
| `GoogleAuthInitView` | Google OAuth2 | OAuth2 authorization URL build | Start consent |
| `GoogleAuthCallbackView` | Google token endpoint | OAuth2 code exchange | Get access/refresh tokens |
| `GoogleAuthCallbackView` | Google userinfo | REST GET | Fetch email/name/picture |
| `YouTubePlaylistsView` | YouTube Data API v3 | `youtube.playlists().list` | Fetch playlists |

Tokens are persisted in `UserSocialToken` (see [data-models-backend.md](./data-models-backend.md))
and rebuilt into `google.oauth2.credentials.Credentials` for the YouTube call.

### 3. Backend → PostgreSQL

Standard Django ORM over `psycopg2`; connection is env-driven (`POSTGRES_*`, default host
`db`). Stores `auth_user`, `organizer_usersocialtoken`, and `django_session`.

## End-to-End Auth & Data Flow

```
[1] User clicks "Sign in" (YoutubeHeader)
      GET /api/auth/google/  →  { auth_url }
[2] Browser → Google consent screen
[3] Google → GET /api/oauth2callback/?code&state  (backend)
      exchange code → tokens; fetch userinfo; upsert User; store UserSocialToken;
      mint JWT; Set-Cookie access_token (HttpOnly/Secure/SameSite=None); 302 → /auth/callback
[4] Frontend /auth/callback → router.replace("/")
[5] Header: GET /api/auth/me/ (cookie) → shows avatar
[6] PlaylistsPage: GET /api/youtube/playlists/ (cookie)
      backend → YouTube Data API → raw response → frontend maps to PlaylistCard grid
```

## Cross-Cutting Invariants

- **HTTPS everywhere, even locally.** `SameSite=None` cookies require `Secure`, which
  requires TLS. Self-signed certs are generated by `bin/generate-all-certs.sh`.
- **Credentialed CORS.** `CORS_ALLOW_CREDENTIALS = True` with a single allowed origin. Do not
  broaden the origin or drop credentials — the whole flow depends on it.
- **Cookie → header bridge.** `JWTAuthCookieMiddleware` is the seam that lets a cookie-based
  frontend talk to header-based DRF SimpleJWT. Changing cookie name/flags breaks integration.
- **Ports differ (3000 vs 8000)** → this is a cross-origin, cross-port setup; every browser
  call to the backend must be credentialed.

## Shared Dependencies

None at the code level — the two parts share no code package. The contract between them is the
REST API shape plus the cookie/CORS configuration. There is no shared TypeScript types package
yet (the target frontend doc references one as the intended source of truth for API shapes).
