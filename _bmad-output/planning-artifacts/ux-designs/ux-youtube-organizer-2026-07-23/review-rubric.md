# Spine Pair Review — youtube-organizer

## Overall verdict

**Adequate, with a contract-blocking tail.** The shape is right and the inheritance is honest: DESIGN.md carries all eight canonical sections in order, EXPERIENCE.md carries every required default plus two invented sections that genuinely earn their place, every `sources:` path resolves, every `{token}` reference in both files resolves to a defined token, and all four PRD journeys are present with named protagonist, numbered steps and climax beats. The editorial voice in DESIGN.md is the strongest thing here — the subtractive thesis is argued, not asserted, and a downstream reader will understand *why* the palette is empty.

What stops it being a clean contract is a narrow band of specifics: one critical token defect (dark-mode selection checkbox), two places where DESIGN.md and EXPERIENCE.md say different things about the same status treatment, a load-bearing component (the inline banner) that six state rows depend on and neither spine defines, and the entire under-player column — a decision the memlog explicitly made — missing from both files. Both visual studies in `.working/` are orphans and the spines-win-on-conflict rule is never stated.

Nothing here is structural. It is a focused list: fix the dark pairs, resolve the two contradictions, define four missing components, add an error-state row, and link the two HTML studies.

## 1. Flow coverage — adequate

UJ-1 and UJ-2 carry explicit `Failure:` lines. Re-ordering to 2·3·1·4 is deliberate (phase-first) and labelled. Also walked every PRD FR for a landing surface.

Search is the sharper miss: FR-14 is Phase 1 and the payoff journey uses filter chips only, so the app's global search has zero narrative validation. *Fix:* either add a beat (UJ-3 step 2 could route through search rather than a chip, and UJ-4 could pass through Trash), or soften the claim to name which surfaces are journey-covered and which are utility surfaces reached but not narrated.
- **medium** UJ-3 and UJ-4 have no failure path (EXPERIENCE.md:259-292). UJ-3's two closers are *variants* (cooking, nothing-fits), not failures — and UJ-3 is the flow that touches the embedded player, the one component with a documented platform limitation (PRD R2) and a documented failure mode (FR-19 unavailable). - **low** UJ-3 renders the watched threshold as *"At ~90%"* (EXPERIENCE.md:270). ## 2. Token completeness — thin

Extracted all 22 color tokens, 8 typography roles, 5 radii, 9 spacing tokens and 10 component entries from DESIGN.md frontmatter, then extracted every `{path.to.token}` reference across both files (44 distinct in DESIGN.md, 2 in EXPERIENCE.md). **Every reference resolves to a defined token — no dangling refs in either file.** The failures are in definition completeness and in contrast, not in resolution.

### Findings

- **critical** `selection-check-bg` and `selection-check-fg` have no `-dark` pairs (DESIGN.md:34-35), while `selection-ring` immediately above them does (DESIGN.md:32-33). They alias to `{colors.foreground}` / `{colors.background}` — the *light* values. A consumer resolving the frontmatter literally renders the dark-mode selection checkbox as near-black `#18181B` fill with white-`#FFFFFF` check, on a dark ground, on top of a thumbnail. Selection is the most frequently rendered state in the app (DESIGN.md:193 says so explicitly), and dark mode is a hard pre-PR gate (`Docs/FRONTEND-STACK.md` §8). *Fix:* add `selection-check-bg-dark: '{colors.foreground-dark}'` and `selection-check-fg-dark: '{colors.background-dark}'`.
- **high** `surface` / `surface-dark` are presented inside the block headed *"Every shadcn `neutral` token is inherited UNCHANGED"* (DESIGN.md:11-20), but **shadcn has no `surface` token.** `#F4F4F5` is shadcn's `muted`/`secondary` value. The whole colour contract is "inherit, don't invent", and the second-most-used colour token in the file is an invention wearing an inheritance label. A downstream implementer has no CSS variable to map it to. *Fix:* rename to `muted` (or `secondary`) to match the shadcn variable it actually is, or move it below the "app-specific additions" divider and say what it maps to.
- **high** No contrast target is stated anywhere in DESIGN.md, and at least one load-bearing pair fails AA. `tag-chip` is `{colors.muted-foreground}` `#71717A` on `{colors.surface}` `#F4F4F5` at `{typography.micro}` 10.5px (DESIGN.md:139-144) — **≈4.40:1, below the 4.5:1 AA floor for normal-size text.** The dark pair (`#A1A1AA` on `#18181B`) is ≈6.9:1 and passes. EXPERIENCE.md:199 asserts the floor is satisfied by inheritance — *"shadcn `neutral` ships WCAG AA-compliant defaults; no brand override exists to compromise them"* — which is true of shadcn's own pairings but not of this app-specific one. *Fix:* state AA targets for the app-specific pairs; for tag chips either raise to `{colors.foreground}`, drop the surface fill, or size up from `micro`.
- **high** The z-order of the status scrims against the thumbnail's own furniture is unspecified, and the naive reading breaks the duration badge. `watched-scrim` is `rgba(255,255,255,0.55)` applied to *"the whole thumbnail"* (DESIGN.md:194, 260); `duration-badge` is `#FFFFFF` on `rgba(0,0,0,0.82)` sitting bottom-right *on* that thumbnail (DESIGN.md:122-127). Scrim over badge turns an 82%-black chip into mid-grey with white text in light mode. Same question applies to the selection checkbox and the 3px outline. *Fix:* one sentence in §Components — scrim sits below the badge/checkbox/outline layer, or the badge gets an opaque fill.
- **medium** The "reference only" inheritance list names twelve tokens (DESIGN.md:12-14) but writes down only six of them plus dark pairs; `card`, `popover`, `input`, `ring`, `secondary`, `destructive-foreground` are declared inherited and then never appear. The block's own stated rationale — *"written down because the whole visual identity rests on them"* — argues for all or none. *Fix:* complete the list or trim the comment to say the written subset is the load-bearing subset.
- **low** `typography.numeric` has no `lineHeight` while all seven siblings do (DESIGN.md:86-90), and the prose says *"Seven roles"* (DESIGN.md:200) over a table of seven while the frontmatter defines eight. `numeric` is real and referenced twice. *Fix:* add the lineHeight, say eight.
- **low** Microcopy placeholders use the same brace syntax as token cross-references: `"No matches for `{query}`"` and `` "`{Playlist name}` is empty" `` (EXPERIENCE.md:151, 153). A source-extractor resolving `{path.to.token}` will pick these up as unresolvable tokens. *Fix:* switch copy placeholders to a different delimiter (`<query>`).

## 3. Component coverage — thin

### Findings

- **high** **The inline banner has no definition on either side.** Six state rows and one component row depend on it — import running, import complete, import partial failure, pending-clear orphans, quota exhausted, read-only scope (EXPERIENCE.md:104, 154, 156-159) — and it is the specified alternative to a modal, so it is doing real anti-blocking work. - **high** **Triage row is visual-only.** DESIGN.md:264 specifies it (checkbox, 34px thumb, 1-line title, right-aligned duration); EXPERIENCE.md §Component Patterns has no row for it. The consequence is a genuinely undecided interaction on the app's densest surface: on the card, *"click the thumbnail opens Watch"* (EXPERIENCE.md:96) — on a triage row, does clicking the row open Watch, toggle selection, or neither? List mode is the default triage mode, so this is the most-executed click in the product. *Fix:* add a Triage row entry to §Component Patterns naming the row click target, the thumbnail click target and the touch behaviour.
- **high** **The watch-page under-player column is absent from both spines.** memlog:34 resolved it in full — title, channel, duration, then an inline-editable tag row, description collapsed behind "more", and a Phase-2 playlist-position line (`4 of 9 — Guitar Course Vol.1`) with **manual** prev/next. Of that, only the inline tag row survives (EXPERIENCE.md:100) and the description toggle appears once as a noun in a list (EXPERIENCE.md:54). **Playlist position and manual progression appear nowhere in either file.** That was the decision that resolved the no-rail consequence memlog:33 raised; dropping it re-opens it, and leaves the one place autoplay-avoidance has to be enforced structurally with no home. *Fix:* add a "Watch page column" component to both spines carrying the memlog:34 anatomy and the manual-advance rule.
- **high** **The expired-freshness marker is specified to exist with no form.** EXPERIENCE.md:97: *"Freshness renders nothing until the perishable window has expired, then a marker appears."* No marker is defined in DESIGN.md — no token, no component, no anatomy. PRD FR-18 assigns exactly this decision to UX (*"a freshness cue is shown on Video cards; exact form is a UX decision"*), and memlog:45 item 6 flags it as *"a genuine gap, not an invention."* Neither spine flags it as open, so downstream will invent one. *Fix:* decide it (an icon in the status layer, consistent with the achromatic rule), or mark it explicitly unresolved so it is not silently guessed.
- **high** **Watched treatment contradicts itself across three passages and the PRD.** DESIGN.md:194 and :260 = dim only, and *"never by a colored badge."* EXPERIENCE.md:97 = *"Watched dims the thumbnail"* — dimming only. EXPERIENCE.md:205 (Accessibility Floor) = *"Watched, unavailable, and expired are dimming plus an icon or label, never a colored dot."* PRD FR-16 and memlog:41 = *"shown as a badge"* / *"dims the whole thumbnail (plus badge)."* Dim-only is opacity-alone signalling, which the accessibility section two sections later forbids. *Fix:* commit to dim + achromatic icon/label everywhere, and make DESIGN.md's "never a colored badge" read as "never a *colored* badge" without implying no badge.
- **high** **Unavailable scope conflicts between spines.** DESIGN.md:260: *"All status renders on the thumbnail, never in the card body… Watched and unavailable apply their scrim to the whole thumbnail."* EXPERIENCE.md:97: *"Unavailable dims the whole card."* memlog:41 sides with EXPERIENCE (*"greys out the entire card"*). A consumer building the card has to guess whether the title and tag row dim too. *Fix:* pick one — card-level dimming for unavailable is the better read, since the whole object is dead, but then DESIGN.md's "never in the card body" needs the exception carved out.
- **medium** **View toggle** has a behavioral row (EXPERIENCE.md:102, including the non-obvious per-surface persistence rule) but no visual spec or frontmatter token in DESIGN.md. It is persistent chrome on three surfaces. *Fix:* add a `view-toggle` component entry.
- **medium** **Sidebar nav item** is the mirror case — visual spec at DESIGN.md:266, no behavioral row. The Phase-2 IA promises *"Playlists ... expandable by name"* (EXPERIENCE.md:36) and no expand/collapse behaviour is specified anywhere. *Fix:* add a Sidebar behavioral row covering active state, expansion, and the mobile drawer equivalent.
- **medium** **The Freshness control is undefined.** The bulk action bar's Freshness action (EXPERIENCE.md:99, 122) must set Evergreen *or* Perishable **plus a window** (FR-17) — the window is a value the user has to enter. No popover, no control, no input is specified on either side, and this is the one triage action that cannot be a single tap. *Fix:* specify the control and confirm it still satisfies the ≤2-interaction bound.
- **medium** **The triage mode switch has no affordance.** Two modes are the product's core contract (EXPERIENCE.md:106-142) and *"the user switches freely"* — but no control, no keyboard shortcut (the map at :171-184 has none), and no visual spec exists for the switch. *Fix:* add the control to §Component Patterns and a key to the map.
- **medium** **"Filing as: `guitar`"** — the pinned header that defines Focus mode (EXPERIENCE.md:130) has no component on either side. *Fix:* one row, both spines.
- **medium** **Playlist reorder has no mechanism.** FR-10 requires ordered playlists with reorder; the IA promises it (EXPERIENCE.md:37). Drag is neither specified nor banned, hover-only affordances are banned (EXPERIENCE.md:192), and touch is first-class — so the obvious implementation is blocked by an adjacent rule and no alternative is given. *Fix:* specify move-up/move-down controls or explicitly allow drag with a touch equivalent.
- **low** Component names differ across the pair: "Selection treatment" (DESIGN.md:261) vs "Selection" (EXPERIENCE.md:98); "Filter chip" (DESIGN.md:263) vs "Filter chip row" (EXPERIENCE.md:101). Mechanical name-matching across the spines fails on both. *Fix:* pin one name each.

## 4. State coverage — thin

Walked all twelve IA surfaces against the six state classes (empty, cold-load, error, offline, permission-denied, partial). Coverage is genuinely good on the two Phase-1 workhorses — Library and Uncategorized carry cold load, empty, import-running, import-complete, import-partial, orphans, quota-exhaustion and read-only-scope between them, and the partial-triage state is handled as a first-class concept rather than an error. The holes are the surfaces that were not the focus, and one whole state class.

### Findings

- **high** **No generic fetch/server-error state exists on any surface.** The State Patterns table's only failure-of-loading row is Offline (EXPERIENCE.md:163). A 500, a timeout, or a failed query on Library, Search, Watch or Playlist detail has no specified treatment, so every consumer invents one. This is the one state class with zero coverage. *Fix:* one generic row — *"Load failed | Any surface | Inline error in the content region with a retry action; the shell and nav stay usable"* — plus the dry-voice copy.
- **high** **No auth-expired / token-revoked / signed-out state.** The app holds a YouTube **write** scope (PRD R3, higher token-handling stakes) and is meant to be used for years. Revocation, expiry, and Google-side consent withdrawal are certainties, and the only auth-adjacent row is read-only-scope-granted (EXPERIENCE.md:159). *Fix:* add a row covering re-auth — the app should keep serving the local Library read-only and confine the prompt to sync/playback actions.
- **medium** Six IA surfaces have zero rows in State Patterns: **Tags, Trash, Needs review, Watched, Playlists (index), Migration.** For two of them the missing state is the *normal* one — empty Trash and empty Needs review are what the user sees most of the time, and "Needs review is empty" is the success condition of UJ-4. Migration has no no-playlists-found and no auth-failure state despite being a first-run surface. *Fix:* add empty rows for all six; Migration also needs a partial/failed row (its flow has one at EXPERIENCE.md:283 but the table does not).
- **medium** Watch has no cold-load and no player-failed-to-embed state — only "unavailable" (EXPERIENCE.md:160). The embed can fail for reasons other than the video being gone (network, blocked embed, region), and FR-19's rule is *"never a broken player."* *Fix:* one row distinguishing "unavailable at source" from "embed failed to load."
- **medium** Trash restore has no behaviour anywhere in either spine. The IA promises *"restorable within the retention window"* (EXPERIENCE.md:34) and the confirmation copy promises 30 days, but no restore action, no expiry treatment, no purge, and no empty-trash state is specified. *Fix:* a Trash row in §Component Patterns and an empty state.
- **low** Search has no cold-load / in-flight state (EXPERIENCE.md:151 covers only zero results), and UJ-4's opening beat — the quiet inline notice *"14 videos are past their watch-by window"* (EXPERIENCE.md:287) — is a state with no row in the table. *Fix:* add both.
