- (decision) Anti-doomscroll is a hard DESIGN constraint, not just a product goal (PRD 8): surfaces must not reproduce infinite chronological feeds, and must not expose YouTube recommendation/autoplay machinery inside the app. This constrains the browse surface, the player, and any 'related' affordance.
- (decision) Triage throughput is a bounded NFR (PRD 8, load-bearing for counter-metric SM-C2): filing ONE video takes <=2 interactions; applying a tag/attribute to a multi-selection is a SINGLE action. No per-video modal gauntlet. This is the hardest constraint on the triage surface design.

Needs a UX answer for how Uncategorized is surfaced without becoming a guilt-pile badge.
- (decision) CORE VISUAL THESIS (Alexis, verbatim intent): the app SHOULD look like YouTube -- deliberately, not accidentally. He loves YouTube; the familiarity is a feature. 'It's the same content, but I'm seeing it the way I want it and not the way the algorithms and the big companies want me to consume it.' Design strategy is therefore SUBTRACTIVE, not differentiating: keep YouTube's visual language and muscle memory, REMOVE the machinery. This OVERRIDES the earlier reading that anti-doomscroll implies a visually distinct product -- the anti-doomscroll is achieved by removal, not by unfamiliarity.
- (decision) SUBTRACTION LIST (what YouTube's UI has that this app must NOT have): recommended/suggested video sections, comments, related-videos sidebar, autoplay-next, algorithmic feed. The app shows ONLY content Alexis saved into it. This is the concrete UI expression of PRD 8 anti-doomscroll NFR.
- (decision) FAMILIARITY AS A REQUIREMENT: 'I want to be comfortable enough and familiar enough and not to feel that it's a completely different environment.' Zero learning curve is an explicit goal. Novel interaction patterns must be justified by need (e.g. bulk triage has no YouTube precedent); everywhere else, default to the YouTube-shaped affordance.
- (decision) VIDEO CARD content model (Alexis's own spec): YouTube-style card showing (1) video thumbnail image, (2) title, (3) channel title, (4) THE TAGS HE ADDED. Tags are the app's addition to the YouTube card -- YouTube cards have no tag row. This is the single most important component in the system; it appears on every browse and triage surface.
- (decision) TWO VIEW MODES, user-toggleable: grid/thumbnail view ('thumb view') and list view. Mirrors YouTube's own grid-vs-list duality. Toggle state should persist. Density differs between the two -- list view is the natural fit for high-volume triage, grid for browsing by mood.

- (decision) COLOR STRATEGY: red is reserved for DESTRUCTIVE/danger semantics ONLY. Brand is neutral -- no red brand accent, no red logo mark, no red active-nav pill. shadcn destructive semantics stay untouched. Consequence: the YouTube familiarity Alexis wants is carried STRUCTURALLY (layout, card shape, grid/list duality, sidebar chrome) rather than CHROMATICALLY. This is coherent -- YouTube's own UI is ~95% neutral -- but it means the palette does none of the familiarity work, so layout and component shape must do all of it.

- (decision) TRIAGE = TWO MODES, both required. (1) LIST MODE (default, general-purpose): Gmail-shaped -- row checkboxes, bulk action bar appears on selection with Tag/Freshness/Discard, shift-click ranges + j/k/x/t keyboard on desktop, tap-to-select on touch. Handles mixed batches, discards, freshness. (2) FOCUS MODE (tag-first bucketing): user picks the target tag FIRST, then sweeps toggling matches, then one Apply action files the whole selection. Inverts the question from 'what tags does this video need' to 'which of these are guitar'. Matches how a weekly catch actually clusters (guitar / barca / history / podcast); ~4 sweeps clears a 100-video week.
- (decision) Both triage modes independently satisfy the PRD 8 bound: list mode files one video in <=2 interactions (select + apply) and bulk-tags in 1 action; focus mode amortizes to well under 2 interactions per video. Focus mode is the direct mitigation for counter-metric SM-C2 and reduces the pressure to pull FR-8 suggestions forward from Phase 2.
- (decision) WATCH PAGE: NO RIGHT RAIL AT ALL. Centered player, single column. Alexis explicitly rejected filling YouTube's recommendation slot with anything -- including his own curated queue. The rail-shaped hole is not filled, it is REMOVED. This is the strongest anti-doomscroll expression in the design: the app never occupies the screen region where YouTube trains you to look for 'what's next'. Consequence accepted: the watch page is the one surface that will read as visibly NOT-YouTube.
- (decision) MOBILE NAV: bottom tab bar (persistent, thumb-reach, YouTube-mobile-familiar) for the 3-4 highest-frequency destinations, PLUS a drawer holding the full destination list for the rest (Needs review, Trash, Settings). Bottom bar is load-bearing for one-handed touch triage per PRD 8 responsive NFR.
- (assumption) OPEN CONSEQUENCE of the no-rail watch page: (a) inline tag editing mid-watch and (b) Phase-2 playlist position/progression have no home. Both must live BELOW the centered player in the single column, or on a separate surface. Critically, playlist progression must be MANUAL -- autoplay-next is explicitly forbidden by PRD 8 anti-doomscroll NFR, so a playlist cannot advance on its own regardless of where its controls live.
- (decision) UNDER-PLAYER COLUMN (resolves the no-rail consequence): title, channel, duration, then an INLINE-EDITABLE TAG ROW -- click a tag to edit/remove, add new tags without leaving the watch page. Description collapsed behind a 'more' toggle, YouTube-style. Phase-2 playlist position renders as a quiet '4 of 9 - Guitar Course Vol.1' line with MANUAL prev/next controls; never auto-advances (PRD 8 forbids autoplay machinery). Preserves the mid-watch 'this should be tagged history' moment without reintroducing a rail.

No exclamation marks, no encouragement, no personality, no brand performance -- it is a tool Alexis built for himself and there is no audience to perform for. Full sentences (not the blunt-fragment register), but zero warmth-signaling. Applies to confirmations, toasts, empty states, and errors alike.
