- (decision) Product reframe: the app is a personal CURATION LIBRARY where YouTube is only a source; NOT a YouTube-playlist CRUD client. YouTube's Watch Later = inbox/staging; user periodically triages videos out of WL into app-owned organization, then clears WL.
- (decision) Core value = anti-doomscroll: browse saved videos BY INTENT/MOOD/CONTEXT (e.g. 'long podcasts for cooking by theme', 'concert mood', 'history') instead of chronological Watch Later scrolling.
- (decision) Organization dimensions user wants: own playlists, themes, per-channel, tags, and context/mood buckets. All organization lives in the APP, user wants ZERO playlists on YouTube.
- (decision) Scope: single-user, personal tool for Alexis only. No multi-user/sharing.
- (assumption) Current build has only UserSocialToken model + OAuth; none of the organization data model exists yet. BACKLOG.md frames app as thin YouTube-playlist CRUD wrapper (list/create/delete YT playlists, quota tracking) — MISALIGNED with the curation-library vision; salvage little, then delete in favor of BMAD epics/stories.
- (event) RISK flagged: YouTube Data API has not permitted access to the 'Watch Later' (WL) playlist since ~2016; the exact 'pull from WL + remove from WL' loop may be infeasible via official API — needs validation, may reshape the import mechanism.
- (decision) Working mode: Coaching path, 'personal but built for real' stakes (~4-6pg focused-but-rigorous PRD). Entry point: Journey-led (product value is entirely experiential — two core loops: triage-the-inbox and find-something-to-watch-by-mood).
- (decision) ON-RAMP resolved: user designates ONE normal YouTube playlist ('_Inbox') as the capture target instead of Watch Later. App reads it via YouTube Data API and removes items after import (auto-clear). Preserves the envisioned pull+clear loop; one-time habit swap WL->_Inbox.
- (decision) IMPLICATION of _Inbox on-ramp: app needs YouTube WRITE scope (youtube.force-ssl or playlist write) to delete items from _Inbox after import. Increases OAuth scope + adds quota cost per removal. Read alone is not enough.
- (decision) Categorization is MANUAL by user. App MAY offer suggestions/recommendations, but user always decides and confirms. No silent auto-categorization.
- (decision) THREE distinct journeys identified: (J0) one-time first-run MIGRATION of existing YouTube playlists; (J1) recurring weekly INBOX TRIAGE; (J2) payoff RETRIEVAL by intent/mood/time-budget. Plus an ongoing CURATION/pruning concern.
- (decision) J0 First-run migration: app lists all existing YouTube playlists -> user selects which to import -> success notification -> app replicates YT playlist structure (videos grouped by their playlist) -> then OPTIONALLY offers to delete the YouTube playlists. Every deletion requires explicit confirmation to prevent accidental loss.
- (decision) J1 Weekly triage: import _Inbox -> imported videos land as 'Uncategorized' (a system list/bucket) -> user manually moves them out into their organization later. Expected volume ~100 videos/week.
- (decision) Video attributes the user thinks in (taxonomy backbone): THEME (Music/photography/history...), CHANNEL (from source), URGENCY/time-sensitivity (interest decays with time; match results & news are perishable vs evergreen tutorials), LENGTH/duration, FORMAT/DEPTH (podcast vs full content vs shallow content).
- (decision) CURATION is a core value: user wants a LEAN library, NOT thousands of unwatched videos. Implies pruning/discard flow, likely tied to the urgency-decay dimension (surface perishable/stale videos for watch-or-remove).
- (decision) J2 Retrieval scenarios (concrete): 'I have 1 hour to improve guitar -> find guitar tutorials/courses' (intent+time-budget+theme); 'I'm in the mood for FC Barcelona -> watch Barca videos' (mood+theme/channel). Browse-by-intent, not chronological.
- (event) TENSION to resolve: ~100 videos/week land in Uncategorized but categorization is manual -> triage UX must be FAST (bulk multi-select, bulk-assign, keyboard/quick actions, optional app suggestions to confirm) or Uncategorized becomes a new doomscroll.
- (decision) ORG MODEL locked (Facets + Playlists shape): TAGS (free-form multi-label; absorbs theme+format like history/music/guitar/barca/podcast) + CHANNEL (auto facet from source) + LENGTH (auto duration facet, used to filter out too-long/too-short) = the FIND layer. PLAYLISTS (hand-built, ordered, curated) = the CURATE layer. 'Uncategorized' = system bucket from _Inbox. A video carries facets AND can belong to playlists.
- (decision) DECAY = active shelf-life + prune nudges. User marks a video evergreen OR perishable (with a watch-by/shelf-life window); app tracks age, shows freshness cues, and proactively surfaces expired perishables for bulk watch-or-discard. Directly serves the 'lean library' goal. This is a distinctive/differentiating feature, not just a tag.
- (decision) PLAYBACK: embedded YouTube IFrame player is primary, WITH an 'open in YouTube' option. Anti-doomscroll: no YT sidebar/autoplay inside the app. Auto-mark-watched when a threshold % of the video is played (app tracks progress via IFrame Player API).
- (decision) WATCHED lifecycle: mark watched (auto at % threshold) -> video STAYS in place with a 'watched' badge; user manually keeps/deletes later. (Not auto-archived.)
- (decision) FORM FACTOR: responsive, desktop AND mobile both first-class from day one. Triage UX must work with keyboard (desktop) AND touch (mobile).
- (event) RISK #2 flagged: user wants playback to CONTINUE when phone is locked / app loses focus. Background & lock-screen playback of embedded YouTube is effectively blocked on mobile browsers (media pauses on tab-blur/lock) and is a YouTube Premium-gated behavior the IFrame embed does not permit. Likely INFEASIBLE for an embedded web player; needs explicit decision (accept limitation / native-app path / audio-only workaround / Premium).
- (decision) BACKGROUND PLAY resolved: accept the web limitation (embed pauses on lock/blur); provide 'open in YouTube' handoff for the cook-while-listening/background-audio case (works via YT app + Premium). Background play is NOT an MVP requirement; no native app forced.
- (change) Removed BACKLOG.md (git rm) — PRD supersedes it; avoid multiple sources of truth. User approved.
- (decision) MODEL FIX: introduce LIBRARY as the canonical container. A Video ALWAYS lives in the Library, independent of Tags/Playlists. Playlists & Tags are optional overlays. 'Uncategorized' = derived view of Library videos with no Tags AND no Playlist membership (self-clearing once organized). Deleting a Video from the Library is an explicit action that removes it entirely (and from all playlists); removing from a Playlist only drops membership.
- (decision) SEARCH scope (FR-13): search across Title, Description, Channel name, and Tags; global across Library, and scopeable within a Playlist/current view.
- (decision) _Inbox is set via UI selection from the user's listed YouTube playlists, persisted per-user in the app DB (NOT an env var); changeable anytime. App can create an _Inbox playlist if none exists.
- (decision) Stored per Video (FR-5): add DESCRIPTION and PUBLISHED (posted) date to the metadata; also store IMPORT date (when it entered the app) and SOURCE-ADDED/saved date (when added to the source playlist). Enables pruning by age ('delete everything I saved 3 years ago') and date-based browse/filter.
- (decision) FR-13 date filtering is a TIME-LAPSE RANGE (from-to, either bound optional) over any of the three dates (imported / source-added / published) — supports 'before 2023', 'after Jun 2024', 'between X and Y'. Enables bulk age-based pruning.
