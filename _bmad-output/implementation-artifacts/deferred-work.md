## Deferred from: code review of 1-2-layered-backend-package-skeleton-and-test-runner (2026-08-12)

- **The layering guard's relative-import resolution ignores `node.level` and the containing package.** `backend/organizer/tests/test_layering.py:33-35` maps `from .x import y` to `organizer.x` regardless of depth or which layer directory the file sits in. A future `organizer/services/youtube.py` imported as `from .youtube import client` resolves to `organizer.youtube` and is reported as a violation — a false positive whose likely "fix" is weakening the rule. Dev Notes documented the coarseness deliberately ("tighten it then"); the packages are flat today, so this is real but not yet reachable.

- **`google_auth_views.py` is outside every scanned layer directory and does violate the contracts the new docstrings state.** It is an `APIView` that builds a YouTube Data API client and executes a request inline (`:139-171`) and writes `UserSocialToken` directly (`:118`) — the API layer calling the gateway, and state mutated without passing through services. Story Question #2; the move belongs to 1.4/6.1, both of which rewrite the file. Consequence to carry: the AD-1 guard shipped as "proven to bite" has never run against a single real import, so its green result carries no information until this file lands inside a scanned layer.

- **`coverage` is pinned into the runtime dependency set.** `backend/requirements.txt:17` is consumed wholesale by `backend/Dockerfile:6-7`; there is no dev/test split, so test instrumentation ships in the production image. Cheap now, and every later test-only dependency (factories, fakes, 1-4's test client helpers) follows the precedent set here.

- **Three hand-maintained, divergent lists of "layers".** `test_skeleton.py:7-16` has eight entries (including `organizer.tests`, not an architectural layer), `test_skeleton.py:46-47` has five, `test_layering.py:15-19` has three. Adding a layer requires remembering all three; forgetting the third silently produces an unguarded layer. One declaration with per-layer flags eliminates the class.

- **`.githooks/pre-push` claims CI parity it no longer has.** Line 4 states "Runs the same gates as `.github/workflows/ci.yml`", but line 145 runs bare `manage.py test` while CI now runs `coverage run manage.py test`. The story listed the hook as read-only, so it was correctly left alone — but the divergence is in the one file whose entire premise is predicting CI.

## Deferred from: code review of 1-3-first-party-pyjwt-token-issue-verify-module.md (2026-08-13)

- **Access lifetime lives in three unlinked places.** `organizer/auth/tokens.py:38` hardcodes `timedelta(days=1)`, `youtube_organizer/settings.py:16-19` holds `SIMPLE_JWT.ACCESS_TOKEN_LIFETIME`, and `organizer/google_auth_views.py:146` sets the cookie `max_age=60*60*24`. The docstring asserts they match as prose, not as code. Once 1.4 removes SimpleJWT, an operator changing the only knob still visible in `settings.py` silently changes nothing, and cookie and token expiry can drift apart with no test failing. _Reason for deferring: Story 1.4 owns the `AUTH_JWT` settings block that replaces the `SIMPLE_JWT` one — this is the story's own open Question 2._

- **`AUTH_JWT_ACCESS_LIFETIME` is an undeclared, unvalidated setting.** Read via `getattr` at `organizer/auth/tokens.py:51` with no type or sign check, and present nowhere in `settings.py`. An int value raises a bare `TypeError` out of `issue_access_token` (a 500 on the login path); a negative value mints tokens that are dead on arrival. Its only consumers are `override_settings` in tests, so the setting is exercised exclusively in the shape that must never occur in production. _Reason for deferring: the `getattr` default was specified deliberately to keep the settings diff empty; validation belongs with 1.4's settings block._

- **The AD-1 layering guard is blind to non-literal imports.** `_imported_modules` (`organizer/tests/test_layering.py:44-66`) walks only `ast.Import` / `ast.ImportFrom`, so `importlib.import_module("rest_framework_simplejwt")` or `__import__(...)` inside `organizer/auth/` passes green. Also `organizer/tests/` has no `FORBIDDEN` key, so a helper migrated there leaves the scanned set. Pre-existing from 1.2, but newly load-bearing: AC3's standing enforcement now rests entirely on this guard. _Reason for deferring: pre-existing limitation, and closing it means a different detection strategy than the one 1.2 established._

- **`jti` is minted but structurally unusable, and the gap is untracked.** `organizer/auth/tokens.py:64` mints a `jti` that nothing reads and `REQUIRED_CLAIMS` deliberately excludes. Combined with a 1-day lifetime and no session-invalidation check in `get_user_from_claims`, a stolen token is valid for up to 24 hours with no revocation and no server-side kill switch — a regression surface relative to SimpleJWT, which ships blacklist machinery. _Reason for deferring: refresh tokens, rotation and blocklist are out of scope entirely per the story's Dev Notes; this entry exists so the gap is tracked somewhere._

- **The compat suite's removal obligation lives only in a docstring.** `organizer/tests/test_auth_tokens.py:233-241` says "DELETED BY STORY 1.4" in prose; it is recorded neither here nor in the 1.4 story file. The SimpleJWT imports are function-level (`:248`, `:256`, `:270`), so removing the dependency yields three cryptic `ModuleNotFoundError`s at run time rather than one obvious collection failure. _Reason for deferring: the durable place for it is Story 1.4's task list, which does not exist yet._

- **`get_user_from_claims`'s exception net reports genuine defects as 401.** `organizer/auth/tokens.py:113` catches `(KeyError, TypeError, ValueError, DoesNotExist)` and reports all of them as "token does not resolve to a user", so a malformed claims dict from a future caller or a custom user model raising during lookup becomes a 401 instead of the 500 it actually is, with the real cause buried in a chained exception. _Reason for deferring: narrowing it correctly needs 1.4's real call site to know which failures are genuinely client-caused._

- **AC3's DoD grep is case-sensitive, so it is not the check it claims to be.** `grep -rn "simplejwt" backend/organizer/auth/` returns nothing, but two prose "SimpleJWT" mentions (capitalised) remain at `tokens.py:7` and `tokens.py:30`. AC3 itself is met — no import exists — and the Completion Notes disclose this honestly; the point is that the command as written cannot see what it appears to check. `grep -rni` is the real check. _Reason for deferring: cosmetic in this story, and the standing enforcement is the guard entry rather than the grep._

- **AD-1's write ban cannot be expressed by the layering guard inside `organizer/auth/`.** _Reason for deferring: decided during the 1.3 code review — forbidding `django.db` would block `transaction` while leaving `User.objects.update()` open, buying a false sense of coverage, so the `FORBIDDEN["auth"]` tuple stays exactly as Story 1.3 Task 5 specified._ The guard forbids `organizer.api/services/sync/youtube` and `rest_framework_simplejwt`, but a static import check cannot distinguish a read from a write, and `get_user_from_claims` legitimately reads `django.contrib.auth`'s User. Nothing therefore prevents Story 1.4's authentication class from writing application state inside `auth/` — e.g. `User.objects.filter(...).update(last_login=...)` — which is the exact invariant AD-1 exists to protect. **Story 1.4 owns this**: it is the story that adds the code that could write. Options it should weigh: an AST rule that flags `.save()`/`.create()`/`.update()`/`.delete()` call sites inside `auth/` (expressible, unlike an import rule), or an explicit documented carve-out.
