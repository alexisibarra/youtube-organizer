## 2. What went well

**The invariants landed whole, not partially.** AD-14 (SimpleJWT out, first-party PyJWT in) shipped
across three stories with the cookie contract byte-identical at the end. AD-20 shipped with a drill
that was *actually executed* against a throwaway volume, not documented and assumed.

**Verification was behavioural, not self-reported, where it mattered.** The 401→403 trap was asserted
via the presence of `WWW-Authenticate`. The restore was proved by seeded, recognisable rows
(`drill-alice`, `drill-bob`, `drill-carol`) coming back **by name**, not by matching totals.
The coverage gate was proven to fail, not just configured.

**Scope discipline held for five consecutive stories.** Every story shipped with a scope table and
honoured it: 1.1 touched no frontend file, 1.2 left `google_auth_views.py` where it was, 1.4 did not
"fix" CSRF. This worked because `deferred-work.md` gave the thing you were not doing a durable home
with a reason, an owner and a re-target.

**Falsified predictions were corrected, not buried.** Three concrete cases:
`cryptography` was predicted to lose its requirer when SimpleJWT went — it did not (`pyOpenSSL` pins
it), and the entry was rewritten with the reasoning *"a prediction that turned out false is worth as
much as one that came true."* SimpleJWT was documented as casting `user_id` to `str` only for non-int
pks — it is unconditional, found and handled in 1.3. Story 1.5 predicted an 87-test baseline — it was
measured at 93 and corrected in the DoD line rather than rounded past.

**The adversarial review process found real defects, repeatedly.** Not cosmetic ones: a guard blind to
the most idiomatic spelling of the violation it existed to catch (1.2); PyJWT exceptions outside the
`InvalidTokenError` subtree escaping as 500s instead of 401s (1.3); a `trap` handler that let a signal
fall *through* into a destructive `pg_restore` and exit 0 (1.5).

## 3. What was hard

### Pattern A — Guards that certify their own blind spot (3 of 5 stories, identical root cause)

This is the strongest signal in the epic, and it **recurred after we already knew about it**:

- **1.2** — the AD-1 layering guard was blind to `from . import youtube` / `from organizer import
  youtube` / `from django import http`. The DoD's "proven to bite" exercise used `import
  rest_framework`, which happens to hit the one detection path that worked, so the proof never
  covered the gap.
- **1.4** — the new write-guard was blind to Django 6's async ORM (`await user.asave()`) and to a
  queryset held in a local (`qs = User.objects.filter(...)` then `qs.update(...)`). The review named
  it explicitly: *"the 1.2 failure mode repeating in the new detector."*
- **1.5** — the `--single-transaction` assertion was a whole-file text search. It passed on the
  **comment explaining the flag** and stayed green when the flag was deleted from the actual command.

**Root cause, identical every time:** the guard's self-test enumerates only forms the detector already
handles. A meta-test built that way cannot fail, so it ratifies the hole instead of exposing it.

### Pattern B — Authoritative documents lagging the code

`CLAUDE.md` makes `Docs/CI-AND-GITHUB-GATES.md` and `_bmad-output/project-context.md` binding — they
win over code on conflict. Both were found stale in the 1.2, 1.3 **and** 1.4 reviews: at one point the
CI doc asserted a coverage gate that did not exist, and `project-context.md` documented SimpleJWT and
`JWTAuthCookieMiddleware` as the live auth mechanism after both had been deleted.

A binding document that is three stories out of date is worse than no document — it is a wrong answer
carrying authority.

### Pattern C — DoD lines ticked for checks that cannot produce that output (4 of 5 stories)

Under a section header that reads *"verifiable, no self-reporting"*:

- 1.2's `python -c "import organizer.api, …"` raises `ImproperlyConfigured` as literally written
- 1.4's `grep -rni "simplejwt" backend/organizer/` is unsatisfiable by that same story's Task 7,
  which requires the literal string to stay in `FORBIDDEN["auth"]`
- 1.5 had two DoD lines that became false during the patch pass and stayed ticked
- 1.1's Task 4 carried a `[~]` marker outside the document's own checkbox vocabulary

Every instance was **honestly disclosed in Completion Notes** — the checkbox simply was not amended to
match. 1.4 set the right precedent by striking such lines through rather than ticking them.

### Pattern D — Review volume compounding, and a patch pass that regressed

Findings per story: 1.1 (15) → 1.2 (24) → 1.3 (23) → 1.4 (39) → **1.5 (40, plus a second pass of 29)**.
Story records grew 438 → 1019 lines.

The 1.5 second pass is the one that matters: **three regressions were introduced by the first patch
pass**, two confirmed by running them — a `trap` handler that resumed into the destructive step after
SIGTERM and exited 0; a guard hardening that blocked restoring into an *empty* database, which is the
primary AD-20 disaster-recovery scenario; and a window where a signal could delete a freshly committed,
verified backup while the script printed success.

The process caught all three. But "a second adversarial pass was needed to catch what the first pass
broke" is a process fact, not a footnote.

## 4. Key insights

1. **A guard is only as good as the case its self-test does *not* already handle.** Prove-it-bites on
   the form the detector was written for proves nothing. Three stories learned this independently.
2. **Documentation declared authoritative must be updated in the same PR as the mechanism it
   describes** — otherwise its authority makes it actively harmful.
3. **A DoD line that cannot be run as written is not a gate.** Strike it, or fix it; do not tick it and
   explain in prose below.
4. **Patch passes are code changes and can regress** — especially in shell and destructive paths, where
   the failure mode is silent and the blast radius is the library.
5. **`deferred-work.md` is the reason scope discipline survived five stories.** It is the epic's most
   reusable asset, more than any code that shipped.
6. **Correcting a falsified prediction is worth as much as confirming a true one.** This team does it,
   and it should be protected as a norm rather than left to individual conscientiousness.

## 5. Next epic preparation — Epic 2: Frontend platform

**Dependency check:** Epic 2 depends on **nothing** (it is parallel to Epic 1 per `epics.md`). No Epic 1
work blocks it, and no Epic 1 discovery invalidates its plan. Epic 3's two shipped stories (3.5, 3.6)
already gave Epic 2 a working CI and pre-push hook to land against.

**Carry-forward concerns:**

- **AI-1 is Epic 2's to fix and belongs to no story yet.** `frontend/src/components/YoutubeHeader.tsx:21`
  calls the Google auth init without `credentials: "include"`, so the session holding `oauth_state` and
  `oauth_code_verifier` is never persisted and the callback raises `MismatchingStateError`. It is the
  **only login entry point for real users**, and it is why 1.4 had to be verified with `curl` rather
  than by clicking Sign in. Story 2.2 deletes the file entirely — the fix must be *carried into the
  rebuild*, not assumed to disappear with it.
- **Story 2.1's pin block is stale by its own admission** (`Next.js ~16.1.6`, "already behind its LTS
  line"). Epic 1 has a proven method for this: verify each pin against the current release at
  implementation time, pin exactly, and record *why* each value was chosen — 1.1's pin block is the
  template.
- **The guard lesson has no carrier into the frontend.** Story 2.5 stands up the Jest/RTL harness and
  the 70% gate. Nothing in Epic 2 currently instructs it to inherit Pattern A's fix, or the 1.2 → 1.4
  sequencing that made the backend gate honest (harness and baseline in one story, `fail_under` turned
  on in the story that makes the threshold genuinely reachable).
- **The backend dev/test dependency split remains unresolved** — `coverage` and `PyYAML` are pinned into
  the runtime `requirements.txt` and ship in the production image. npm gives the frontend
  `devDependencies` for free, so Epic 2 will not repeat it, but the backend precedent stands and each
  new test-only dependency compounds it.
- **Epic 2 is the first epic where the frontend pre-push layers are not skippable** — `npm` on PATH,
  Node matching `frontend/.nvmrc` exactly (`v22.23.2`), and a host `frontend/node_modules`. Worth
  confirming that environment is in place before the first frontend PR rather than discovering it at
  push time.

**Not Epic 2's problem, correctly deferred:** CSRF (Epic 9, where unsafe methods arrive), `SECRET_KEY`
and the production settings split (AD-17), re-running the restore drill against a real library
(Epic 4, once `Video`/`Tag`/`VideoTombstone` exist).

**Significant discovery assessment: NONE.** Nothing Epic 1 uncovered requires re-planning Epic 2.
The epic definitions stand as written.
